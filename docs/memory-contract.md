# Контракт обновления долговременной памяти

Долговременная память — Markdown-файлы в `data/memory/`. Модель **никогда не правит Markdown напрямую**: она возвращает только patch — список операций над записями. `MemoryService` проверяет patch по этому контракту и лишь затем передаёт его хранилищу. Пользователь может править файлы вручную (в UI или редакторе) — это единственный другой путь записи.

Реализация: модели — [`memory/operations.py`](../src/local_agent/memory/operations.py), проверки — [`memory/validator.py`](../src/local_agent/memory/validator.py), тесты — [`tests/test_memory_validator.py`](../tests/test_memory_validator.py).

## Формат patch

```json
{
  "version": 1,
  "operations": []
}
```

- `version` — целое число `1`. Другие версии не поддерживаются.
- `operations` — список, не больше 100 операций. Пустой список — корректный ответ «изменений нет».
- Других полей верхнего уровня нет.

## Операции

| op | Обязательные поля | Смысл |
|---|---|---|
| `add` | `op`, `file`, `section`, `content`, `source_message_ids` | Новая запись в разделе `## section` файла `file` |
| `update` | `op`, `file`, `entry_id`, `content`, `source_message_ids` | Заменить текст существующей записи |
| `delete` | `op`, `file`, `entry_id`, `source_message_ids` | Удалить существующую запись |

```json
{"op": "add", "file": "preferences.md", "section": "Рабочий процесс",
 "content": "Предпочитает небольшие проверяемые изменения.", "source_message_ids": ["<id>"]}
{"op": "update", "file": "projects.md", "entry_id": "<32 hex>",
 "content": "Meepo хранит память в Markdown.", "source_message_ids": ["<id>"]}
{"op": "delete", "file": "decisions.md", "entry_id": "<32 hex>", "source_message_ids": ["<id>"]}
```

## Правила

### Поля
- Никаких полей сверх перечисленных для данного `op`.
- `content` — одна строка, 1–2000 символов. `section` — одна строка, 1–100 символов.
- Строки обрезаются по краям пробелов до проверки.

### Файлы
- `file` — только имя вида `name.md` (`[a-z0-9][a-z0-9_-]*\.md`), без путей.
- Разрешены только файлы, которые уже существуют в папке памяти. Создавать новые файлы модель не может.

### Записи и `entry_id`
- Управляемая запись — строка ровно такого вида: `- <!-- memory:id=<32 hex> --> текст`.
- `entry_id` создаёт хранилище при `add`. Модель его не придумывает и в `add` не передаёт.
- `update`/`delete` ссылаются только на существующий `entry_id`, который встречается во всей памяти ровно один раз и находится именно в указанном `file`.
- Один `entry_id` можно затронуть в patch не больше одного раза.

### Ручные записи
- Любая строка, не совпадающая с форматом управляемой записи, — ручная (в том числе строка, где маркер `memory:id` стоит не в начале).
- Ручные записи модели недоступны: у них нет `entry_id`, поэтому `update`/`delete` до них не дотягиваются.

### Источники
- `source_message_ids` обязательны в каждой операции: непустой список уникальных id.
- Каждый id — сообщение из новых сообщений **текущей** сессии после checkpoint, с `role == "user"`.
- Ответы ассистента и результаты инструментов источником быть не могут: модель видит их только как контекст.

### Дубли
- `add` с текстом, который уже есть в памяти, отклоняет весь patch. Сравнение — после схлопывания пробелов и без учёта регистра, по всем строкам всех файлов (управляемым и ручным) и по предыдущим `add` в этом же patch.
- Дубль не превращается в no-op: валидатор проверяет контракт, а не угадывает намерение модели.
- Для `update` проверка дублей не выполняется.

## Что парсер допускает

Только транспортные мелочи, не меняющие смысла:
- ответ, обёрнутый в блок ```` ```json … ``` ````;
- поле со значением `null`, не относящееся к данному `op` (например, `"entry_id": null` в `add`), считается отсутствующим. Чужое поле с любым другим значением — нарушение контракта.

## Ошибки

Любое нарушение — `MemoryPatchRejected(reason, index)`, где `index` — номер операции (с нуля) или `None` для ошибок всего patch (JSON, версия, лишние поля верхнего уровня).

При отказе:
- patch отклоняется **целиком**, даже если остальные операции корректны;
- память не меняется;
- checkpoint не двигается — при следующем запуске те же сообщения будут обработаны снова.

## Ещё не реализовано

Следующие этапы, вне этого контракта:
- атомарное применение пачки и checkpoint вместе через pending-журнал (сейчас файлы пишутся атомарно по одному);
- запрет файловым инструментам агента писать в папку памяти;
- технический журнал обновлений памяти.
