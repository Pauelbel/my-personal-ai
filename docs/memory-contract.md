# Контракт обновления долговременной памяти

Долговременная память — Markdown-файлы в `data/memory/`. Модель **никогда не правит Markdown напрямую**: она возвращает только patch — список операций над записями. `MemoryService` проверяет patch по этому контракту и лишь затем передаёт его хранилищу. Пользователь может править файлы вручную (в UI или редакторе) — это единственный другой путь записи.

Реализация: модели — [`memory/operations.py`](../src/local_agent/memory/operations.py), проверки — [`memory/validator.py`](../src/local_agent/memory/validator.py), тесты — [`tests/test_memory_validator.py`](../tests/test_memory_validator.py).

## Формат patch

```json
{
  "version": 2,
  "operations": []
}
```

- `version` — целое число `2`. Другие версии не поддерживаются.
- `operations` — список, не больше 100 операций. Пустой список — корректный ответ «изменений нет».
- Других полей верхнего уровня нет.

## Операции

| op | Обязательные поля | Смысл |
|---|---|---|
| `add` | `op`, `file`, `section`, `content`, `source_message_ids` | Новая запись в разделе `## section` файла `file` |
| `update` | `op`, `file`, `old_content`, `content`, `source_message_ids` | Заменить строку с точным прежним текстом |
| `delete` | `op`, `file`, `old_content`, `source_message_ids` | Удалить строку с точным текстом |

```json
{"op": "add", "file": "preferences.md", "section": "Рабочий процесс",
 "content": "Предпочитает небольшие проверяемые изменения.", "source_message_ids": ["<id>"]}
{"op": "update", "file": "projects.md", "old_content": "Старый текст записи",
 "content": "Meepo хранит память в Markdown.", "source_message_ids": ["<id>"]}
{"op": "delete", "file": "decisions.md", "old_content": "Старый текст записи", "source_message_ids": ["<id>"]}
```

## Правила

### Поля
- Никаких полей сверх перечисленных для данного `op`.
- `content` и `old_content` — одна строка, 1–2000 символов. `section` — одна строка, 1–100 символов.
- Строки обрезаются по краям пробелов до проверки.

### Файлы
- `file` — только имя вида `name.md` (`[a-z0-9][a-z0-9_-]*\.md`), без путей.
- Разрешены только файлы, которые уже существуют в папке памяти. Создавать новые файлы модель не может.

### Адресация без ID
- Запись — строка вида `- текст` внутри указанного Markdown-файла.
- `update`/`delete` передают `old_content` — точный текст после `- ` у существующей строки. В указанном файле такая строка должна встречаться ровно один раз.
- Одну и ту же исходную строку нельзя менять дважды в одном patch. Если пользователь изменил её до применения patch, он отклоняется целиком.
- Старые метки `memory:id` автоматически удаляются при открытии хранилища; текст записей сохраняется.

### Ручные записи
- Ручные строки и строки модели больше не различаются по скрытой метке. Модель может предложить точечное изменение существующей строки, но код применит его только при точном единственном совпадении.
- Пересборка файла моделью запрещена. Несвязанные ручные правки сохраняются; при конфликте операция отклоняется, а checkpoint не сдвигается.

### Источники
- `source_message_ids` обязательны в каждой операции: непустой список уникальных id.
- Каждый id — сообщение из новых сообщений **текущей** сессии после checkpoint, с `role == "user"`.
- Ответы ассистента и результаты инструментов источником быть не могут: модель видит их только как контекст.

### Дубли
- `add` с текстом, который уже есть в памяти, отклоняет весь patch. Сравнение — после схлопывания пробелов и без учёта регистра, по всем строкам всех файлов и по предыдущим операциям в этом же patch.
- Дубль не превращается в no-op: валидатор проверяет контракт, а не угадывает намерение модели.
- `update` не может создать дубль уже существующего текста.

## Что парсер допускает

Только транспортные мелочи, не меняющие смысла:
- ответ, обёрнутый в блок ```` ```json … ``` ````;
- поле со значением `null`, не относящееся к данному `op` (например, `"old_content": null` в `add`), считается отсутствующим. Чужое поле с любым другим значением — нарушение контракта.

## Ошибки

Любое нарушение — `MemoryPatchRejected(reason, index)`, где `index` — номер операции (с нуля) или `None` для ошибок всего patch (JSON, версия, лишние поля верхнего уровня).

При отказе:
- patch отклоняется **целиком**, даже если остальные операции корректны;
- память не меняется;
- checkpoint не двигается — при следующем запуске те же сообщения будут обработаны снова.

## Восстановление и технический журнал

Перед изменением Markdown-файлов и checkpoint хранилище записывает `.pending.json` с исходным и новым содержимым затронутых файлов. При следующем обращении незавершённая операция доводится до конца; если файл был изменён вручную после сбоя, восстановление останавливается и требует проверки вместо перезаписи этой правки. Checkpoint записывается последним.

После успешного применения в `.updates.jsonl` добавляется событие с типом изменения, именами файлов, сессией и новым checkpoint (для обновления моделью). Текст записей памяти в журнал не попадает. Повторное восстановление не создаёт дублирующее событие.

Файловые инструменты агента `write_file` и `edit_file` не могут писать в настроенную папку памяти, даже если она находится внутри рабочей папки сессии. Ручное редактирование через раздел «Память» остаётся доступным.
